# Format Docs

## Overview

使用这个 skill 把零散材料整理成中文规划文档。输出要像可以直接交付、复制进知识库或发给同事的文档，而不是提纲草稿。

默认用中文写作，除非用户明确要求其他语言。用户只给碎片信息时，先补齐合理结构，并把不确定内容标为“待确认”或“可按实际环境替换”，不要编造具体数据、负责人、命令结果或环境名称。

## Core Output Format

默认使用下面的 Markdown 层级和编号体系：

```markdown
#### 一、<一级标题>
##### 1.1 <二级标题>
（1）...
（2）...

##### 1.2 <二级标题>
（1）...
（2）...

#### 二、<一级标题>
##### 2.1 <二级标题>
（1）...
```

格式要求：

- 一级标题使用 `#### 一、`、`#### 二、`、`#### 三、`。
- 二级标题统一使用 `##### 1.1`、`##### 1.2`、`##### 2.1`，不要混用 `######`。
- 二级标题编号必须跟随一级标题变化：第一章用 `1.x`，第二章用 `2.x`。
- 条目使用中文括号编号：`（1）`、`（2）`、`（3）`。
- 命令、变量、路径、服务名、配置项用反引号包裹。
- 连续命令或配置片段使用 fenced code block。
- 解释性提醒使用 blockquote，例如 `> tip：...`。
- 不要在最终文档外额外解释“我做了什么”，除非用户要求说明修改思路。

## Writing Workflow

1. 识别用户材料的主题和目标读者，例如部署规划、开发计划、迁移方案、操作手册、排期规划或技术方案。
2. 将内容归并成 2-5 个一级章节。优先使用动宾结构或名词短语，例如“服务编译部署”“环境准备”“风险与回滚”“后续 TODO”。
3. 每个一级章节拆成 1-4 个二级小节。二级标题要具体，避免“说明”“其他”这类空标题。
4. 将散点材料改写成可执行条目：先说明对象，再说明动作、输入、输出或注意事项。
5. 保留用户给出的真实变量、命令、路径和例子。若需要泛化，只替换可变部分，并说明替换规则。
6. 对缺信息的地方使用“待确认：...”或“可补充：...”，不要让文档看起来已经确认。
7. 最后快速检查标题层级、编号连续性、代码块闭合、术语一致性。

## Content Style

写作风格保持清楚、实用、面向执行：

- 用短段落和列表表达，不写宣传口吻。
- 优先写“怎么做、为什么这样做、怎么验证”，少写抽象背景。
- 对新人可能误解的名词，先放“关键名词说明”小节。
- 对流程类内容，按实际执行顺序组织：准备、编译、部署、查看、登录、验证、回滚。
- 对规划类内容，按目标、范围、方案、里程碑、风险、验收组织。
- 对代码或命令相关内容，给出命令格式、参数含义、示例和注意事项。
- 同一概念只用一个名字；如果存在相近变量，明确区分，例如 `MODULE_NAME` 和 `MODULENAME`。

## Useful Section Patterns

根据材料选择合适章节，不必全部使用：

- `#### 一、背景与目标`
- `#### 二、关键名词说明`
- `#### 三、服务编译部署`
- `#### 四、执行流程`
- `#### 五、验证与排障`
- `#### 六、风险与回滚`
- `#### 七、后续 TODO`

流程小节示例：

````markdown
##### 1.2 启动流程：以<具体例子>为例
（1）编译
格式：编译脚本 服务名
> tip：以下指令只需要把 `<SERVICE_NAME>` 替换成对应服务名。

```bash
./pb_branch_img.sh <SERVICE_NAME>
```

（2）部署测试环境
说明部署模块名、容器名、镜像名之间的对应关系。

```bash
deploy <MODULENAME> --tag=<TAG>
```
````

## Quality Bar

最终文档应该能让读者直接照着执行或继续评审。交付前确认：

- 一级标题和二级标题编号没有跳号或串章。
- 每个小节至少有一个具体动作、说明、规则或待确认项。
- 所有命令都放在代码块里，所有变量名都用反引号。
- 用户给出的例子被保留或自然融入正文。
- 不确定内容被显式标记，没有伪造事实。
